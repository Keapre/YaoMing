# Pusher deploy report

6 August 2026, 10:38

## What is being deployed

| | |
|---|---|
| APK | 79.3 MB |
| native libraries | 23.2 MB in the APK, 23.2 MB once extracted |
| dex handed to dexopt | 34.7 MB across 25 files |
| library packing | stored, so the install does not extract them |

The install is not just a copy. The package manager writes the APK into
`/data/app`, verifies its signature, extracts the native libraries if they are
compressed, and runs dexopt over every dex file. That is why it takes as long
as it does, and it is why the settings below split into transfer and install.

## Measured

Each is a real deploy to the robot. The baseline is what Android Studio does:
one streamed install of the whole APK, no delta, no skipping.

| configuration | time | vs Android Studio | what it did |
|---|---|---|---|
| Android Studio equivalent | 41.5s (±1.0s) | within noise | one streamed session install of the whole APK, no delta |
| pusher, staged install | 42.4s (±711ms) | within noise | push to a temporary file, then install from it |
| pusher, streamed install | 40.4s (±1.2s) | within noise | stream the APK into the install session |
| pusher, delta transfer | 39.3s (±38ms) | 1.1x faster | send only changed chunks, then install |
| pusher, delta + streamed | 42.9s (±463ms) | about the same | changed chunks, streamed into the session |
| pusher, nothing changed | 240ms | 172.7x faster | the robot already holds this exact build |

Best of 3 each. The widest spread between repeats was 1.2s, and differences
smaller than that are reported as noise rather than as a finding.

## What each setting does

`pusher settings` -> Deploy speed

| setting | now | effect here |
|---|---|---|
| Send only changed parts | on | 39.3s vs 42.4s staged (1.1x faster) |
| Skip install when unchanged | on | 240ms when nothing changed |
| Stream the install | on | 40.4s vs 42.4s staged (1.1x faster) |
| Store native libraries | on | stored, so the install extracts nothing |
| Install only changed splits | off | the project builds one APK, so there is nothing to split |

Two of these are not free. Storing the libraries makes the APK bigger, which
costs transfer time, so it is a win on USB or 5 GHz and a question on 2.4 GHz.
Delta costs a little work on the hub to rebuild the APK, which is why it can
lose over USB where the transfer was never the problem.

Not swept here, because changing them needs a rebuild:

- **One ABI** (`pusher slim`): the APK carries 23.2 MB of native libraries. A stock
  project packages two architectures and the hub runs one.
- **Gradle threads**: build time only, nothing to do with the deploy.

## Against Sloth

**Pusher is not a Sloth replacement.** Sloth hot reloads: it sends only the
team's code and loads it into a running app. Pusher installs an APK faster.
Those are different problems, and below a few seconds they are not comparable.

Their published figures, quoted from their README rather than measured here:

| | claimed |
|---|---|
| Sloth, typical | under 1s |
| Sloth, worst case | about 2s |
| FastLoad | about 7s |
| a standard TeamCode upload | 40s+ |

Fastest real deploy measured here: **39.3s** (pusher, delta transfer).

Read that as a floor, not a headline. Everything pusher does still ends in a
package manager install, and no amount of transfer cleverness removes dexopt.
Getting into Sloth's range means not installing at all.
